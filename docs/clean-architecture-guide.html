EmployeeApi / Architecture Notes

Clean Architecture, explained through this API.

A practical guide to the .NET 8 Employee CRUD API, showing where business rules live, how dependencies point inward, and how Dapper calls SQL Server stored procedures without leaking database details into the application core.

1. The central idea

Clean Architecture separates business decisions from delivery mechanisms. The core of the system should not need to know whether requests arrive through HTTP, data is stored in SQL Server, or Dapper is used for mapping.

The dependency rule: source-code dependencies point toward the domain. Outer layers may depend on inner layers; inner layers do not depend on outer layers.

In this project, the domain knows nothing about ASP.NET Core, Dapper, SQL Server, or stored procedures. The application layer defines what it needs through interfaces. Infrastructure supplies the database implementation. The API composes everything and exposes HTTP endpoints.

Domain

Business meaning

Employee represents an employee and its data. This layer is the most stable part of the system. It should contain entities, value objects, and domain rules.

Application

Business use cases

EmployeeService coordinates operations such as create, read, update, and delete. IEmployeeRepository is an abstraction: the application asks for persistence without choosing a technology.

Infrastructure

Technical details

EmployeeRepository implements the application interface. It uses Dapper's CommandDefinition with CommandType.StoredProcedure for every database operation.

API

Delivery mechanism

EmployeesController translates HTTP requests into application calls and translates results into HTTP responses such as 200, 201, 204, and 404.

3. What happens during a request?

  1. The client calls an endpoint.
    POST /api/employees sends a JSON request body to EmployeesController.
  2. The API validates the input boundary.
    Data annotations on CreateEmployeeRequest check required fields, lengths, email format, and salary range.
  3. The application executes the use case.
    EmployeeService maps the request to a domain Employee and calls IEmployeeRepository.
  4. Infrastructure performs persistence.
    EmployeeRepository calls dbo.Employee_Create through Dapper and returns the new ID.
  5. The response travels outward.
    The controller loads the created employee and returns 201 Created with a location for the new resource.

Stored procedures centralize SQL commands in the database. Dapper remains lightweight: it opens the connection, sends named parameters, and maps result rows to the domain model. The application layer does not reference Dapper.

var command = new CommandDefinition(
    "dbo.Employee_GetById",
    new { Id = id },
    commandType: CommandType.StoredProcedure,
    cancellationToken: cancellationToken);

return await connection.QuerySingleOrDefaultAsync<Employee>(command);

5. Why this structure helps

Testability

Application tests can substitute IEmployeeRepository with a fake or mock. They do not need SQL Server running.

Change tolerance

The API contract and use cases can remain stable if the database provider or persistence implementation changes.

Clear ownership

Controllers handle HTTP, services handle use cases, repositories handle persistence, and the domain holds business meaning.

Controlled coupling

Only Infrastructure knows Dapper and SQL Server. Technology-specific dependencies stay at the boundary.

6. Rules to keep the architecture healthy

  • Do not put SQL or Dapper calls in controllers or application services.
  • Do not make the Domain project reference ASP.NET Core, Dapper, or SQL client packages.
  • Define persistence interfaces in Application; implement them in Infrastructure.
  • Keep request and response DTOs at the API/Application boundary instead of exposing database models directly.
  • Keep stored procedure names and parameters explicit and consistent.
  • Validate both API input and database constraints. Validation at one boundary does not replace the other.

7. Run this project

  1. Execute database/001_CreateEmployees.sql.
  2. Execute database/002_EmployeeProcedures.sql.
  3. Set ConnectionStrings:DefaultConnection in src/EmployeeApi.Api/appsettings.json.
  4. Build with dotnet build EmployeeApi.slnx.
  5. Start with dotnet run --project src/EmployeeApi.Api.
  6. Use Swagger or an HTTP client to call /api/employees.
